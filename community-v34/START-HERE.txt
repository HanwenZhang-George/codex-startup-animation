Codex 启动器＋动态壁纸 — V34-r13 适配与稳定性测试完整包

这是完整包：启动动画、流泪转场、常态壁纸、粒子壁纸、全部源码和素材都在内。
这是供另一台电脑本地测试的候选包；尚未替换 GitHub 的 r5。
不包含 CC Switch。不覆盖已有安装，不迁移账号、对话或 API Key。

本次优先测试：
1. 完整解压到新的 r13 目录，保存工作并正常完全退出 Codex。
2. 只点击一次本目录 Launch.exe。记录启动动画和壁纸是否出现。
   如报错或等得过久，按 ESC 后马上运行 Diagnostics\One-Click-Diagnostics.cmd，
   在再次退出或重试前先把 Reports\latest-report.zip 另存并发回；不必强等几分钟。
3. 若正常，保持 Codex 打开，再点击同一个 Launch.exe，检查重复启动。
4. 正常完全退出后，再启动一次。壁纸正常时保持客户端打开并收集报告，
   补充“收集前没有再次退出”。如果一次也没报错，仍发送报告，注明未复现。
报告会分别保留有界的首次失败和后续成功线索；不能保证一次穷尽所有故障。

一、直接运行
1. 完整解压到一个新目录，例如 D:\Codex-Test-r13。不要覆盖旧包，也不要在 ZIP 内运行。
2. 保存工作，在测试电脑上正常完整退出 Codex。
3. 双击新目录最外层的 Launch.exe。无需运行 Install.ps1，也不需要管理员权限。
   没有弹出管理员授权是预期行为；不要通过管理员启动来绕过错误。
   官方桌面图标不会经过此便携包；从官方图标启动不能用来检验本包壁纸。
   如果已经从官方图标打开 Codex，请先正常完整退出，再用本包 Launch.exe。
4. 检查启动画面、流泪和波纹交接、进入 Codex 后的壁纸及输入框透明度。
5. 第一次固定常态视频；之后每次按 75% 常态、25% 粒子选择。
   两次出现之间保持原有 10–15 秒随机间隔。人物暂时离开不代表壁纸坏了。
6. 保持 Codex 打开，再双击同一个 Launch.exe，检查是否再次播放启动动画并回到
   原窗口，且原壁纸继续运行。再测试最小化后点击。不要同时连点启动多个副本。
7. 在首页、对话、项目和设置之间往返，展开/收起侧栏，改变窗口大小，确认输入、
   点击和壁纸正常。多显示器或不同缩放比例请移动窗口后再试一次。
   若启动等待过久，可以按 ESC 跳过并马上收集报告，不必等几分钟。

可选：绑定测试电脑原来的 Codex 桌面图标
便携测试正常后，正常退出 Codex，双击 Install-and-Bind.cmd。
它安装独立副本到当前用户目录，并尝试绑定当前用户桌面唯一的官方 Codex 快捷方式。
不需要每次管理员授权，不修改官方 Codex 程序；原快捷方式会单独备份后再替换。
如果目标安装目录已有文件、找不到唯一可信快捷方式或快捷方式类型不支持，会保守
停止或保留原入口并提示；不要删除其它安装来强行继续。公共桌面不自动处理。
安装后从原 Codex 图标启动，再验证一次重复启动。诊断请使用安装目录里的 Diagnostics，
不要收集旧解压目录的日志。需要还原时使用安装目录 Uninstall.ps1；不要直接删安装目录。

二、独立轻量诊断工具（正式版也保留）
进入 Diagnostics 文件夹，双击 One-Click-Diagnostics.cmd。
固定生成 Reports\latest-report.zip 和 Reports\latest-analysis.txt（中文分析）。
默认先核对全部正式文件 SHA-256 和程序框架，再收集有界的运行与环境记录。
即使校验失败也会继续生成报告。速度取决于磁盘，不需要等动画播放。
新增页面结构计数、窗口筛选原因、相对边距/DPI、内存和驱动版本等数值证据。
进入 Codex 后的布局变化也会按原有频率记录，便于同一份报告分析后续页面故障。
不导出原始 DOM、聊天、窗口标题、用户名、路径、命令行或 API Key。
先完成上面的操作测试，出问题后尽快收集；不用为了生成报告重新启动应用。
报告读取有长度/条数上限，不能保证所有问题都能一次定位。
Check-All-Files.cmd 可单独校验文件，一般反馈只需一键完整诊断。
工具不启动、不关闭、不等待任何应用；不安装东西、不联网、不做整机压力测试。
完整测试顺序见该文件夹 README.txt。结果只放在 Diagnostics\Reports 内。
只保留最新一份，不堆积历史报告。发送 latest-report.zip，并补充哪些现象正常、哪里卡顿。
Ctrl+C 或关闭测试窗口可结束工具。无需在测试机运行 source/tests 开发测试。

三、正常诊断（正式程序保留）
也可以在解压目录打开 PowerShell，运行：
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\Collect-DiagnosticReport.ps1"
它将 ZIP 写入 CodexDiagnosticReports。无需再次启动、等待播放或结束应用。
可通过 GitHub Issues https://github.com/HanwenZhang-George/codex-startup-animation/issues 提交报告，
或发至 hanwen.3.zhang@kcl.ac.uk / zhanghw0511@gmail.com。无需上传整个运行目录。
只输出数值、固定枚举、相对日志类别和允许的兼容标记，不导出原始日志、路径、
账号、聊天、API Key、窗口标题或进程命令行。不要上传运行后的整个目录。
快速报告里的媒体大小检查不等于重新做了哈希校验，更不等于解码成功。
兼容标记只是证据，不等于已证明运行时类型或壁纸传输支持。

四、本次修复和验证范围
本包基于 2026-10-24 重新从原 GitHub 链接下载、核验过的 R10 完整包制作。
不含私人安装配置。这次补齐一种没有默认 main 的官方 page-surface frame 布局。
结构不明确时仍保守拒绝，未知页面不会被强行改成透明。
反馈报告确认布局被拒绝，但没有用户实际 DOM，仍需在反馈电脑确认本次适配结果。
R13 首次启动修复：
- 冷启动页面查询在响应超时后将下一次只读请求上限从 2 秒增至 4 秒；
  总计最多 30 秒，连接动作仅一次且仍有独立上限。不重启客户端、不接收旧请求回复。
- 初始隐藏租约已绑定的窗口，不会仅因新出现隐藏辅助窗口而失去失败恢复机会；
  没有可信租约且窗口有歧义时不猜选，不恢复后来由用户隐藏的窗口。
- 诊断分别记录连接断开类型、当时进程是否退出，以及最终进程退出码。
  正常退出码不等于证明用户主动退出，缺少证据时明确注明不确定。
- 基于上次交付的 R12 封存源码继续修改；没有改动本机私人安装或发布 GitHub。

R12 复核补充：
- 官方快捷方式可选绑定读取当前注册清单中的入口，不再依赖旧的 EXE 文件名。
- 识别期间若官方注册刚好完成版本切换，最多重新发现和验证一次；签名、路径或
  清单异常仍停止，不通过跳过检查来继续。普通更新仍无需手改固定版本或哈希。
- 页面节点原地更新类名、或重新挂载后延迟设置属性时，会重新核验透明样式。
  只观察有限的界面节点，不观察聊天文本，也不新增视频解码器。
- 增加 ESC、迟到回调、重复启动、媒体选择边界、文件被占用、诊断并发等回归。
  覆盖范围及仍需实机确认的边界见 source/tests/reliability-test-cases.md。
- 报告会区分新的公开入口错误与旧的播放成功；日志无法确认操作模式或先后关系时，
  明确标为无法关联，不会拿上一次成功来解释这次点击没有反应。
- 重复启动可以有界恢复选定时已最小化的同一客户端。只允许一次不抢焦点的恢复，
  之后用户主动最小化仍会保留。失败时核对自有窗口位置后补偿，并保留原来的
  最大化恢复状态；不会通过反复强制显示窗口来掩盖失败。
以下 R10 修复继续保留：
- 冷启动按当前用户的官方 Store 注册记录和安装清单找到程序，验证 OpenAI 签名，
  创建后再核对实际进程身份。启动器和壁纸宿主使用同一身份验证实现。
- 本地生成的配置改为自动识别策略，不再保存固定官方版本号和 EXE 哈希。正常的
  Store 版本号、安装路径更新会在下一次启动重新识别，无需每次手工修改地址。
- 已打开的客户端按实际进程和创建时间核验，不会因为发现更新版本而误认另一进程。
- 处理普通窗口在启动期间迟到变为最大化的交接；保留严格的进程、窗口和几何所有权
  检查，避免原来 59% 等待或错误退出。不会通过无限延长超时掩盖问题。
- 媒体保持 R10 原样。分辨率、帧率、透明度、出现概率、视频间隔和资源保护不改。
  原定窗口边距保留；窗口状态交接的修复由独立测试验证。
- 软件将来若改包身份、签名主体、运行时或页面结构，仍可能需要专门适配。此机制
  解决普通版本/路径变化，不能承诺任何未来大改都无需维护。
- 本次修改未在当前电脑的私人安装目录部署，也没有更新 GitHub；先用本包换机测试。

以下 R9 及更早的已验证修复继续保留：
- 修复 r8 壁纸后台准备阶段的第二道内存保护：它此前会在一次低内存预警后永久禁用
  本次壁纸，启动器保留播放请求也无法恢复。现在物理 RAM 偏低或 Windows 低物理内存
  通知不再单独作为停用依据；统一检查当前进程还能使用的提交内存余量。
- 只有可用提交内存低于 512 MiB 时暂停解码；恢复到至少 1 GiB 并连续稳定 30 秒后，
  从同一文件和页面会话恢复。不会重新安装或反复注入，也不会让启动界面等待这 30 秒。
  若内存持续接近耗尽，保持暂停；明确暂停、关闭或禁用仍优先。真实解码/传输错误
  仍可能失败，不能把“请求恢复”当成“已经播放”。报告明确区分这些状态。
- 首次准备遇到真正的内存压力时只保留文件引用，不先创建视频解码器再立刻释放。
  启动器自身内存超限、持续 CPU 超限、身份和完整性校验等保护继续保留。
- 修复只有壁纸后台察觉短暂内存压力、启动器却还在 59% 等待的分支：启动器核验
  同一宿主的新鲜暂停状态后释放启动画面，保留后续播放请求，不伪造准备完成。
以下 r8 修复继续保留：
- 资源保护释放启动动画，同时保留壁纸请求；不会用成功转场掩盖保护退出。
- 报告保留此前资源保护和随后重复启动失败的时间链，增加允许的具体保护原因。
  旧日志没有保存原因时仍显示未知，不把所有资源保护都解释为内存不足。
- 修复后台准备尚在进行时，后续显示请求过早耗尽等待预算并被丢弃的竞争；
  总退出清理仍最多 3 秒，不重试已提交的命令，也不把明确禁用改回开启。
- 失败回滚时，为可能迟到的隐藏请求安排一次不抢焦点的显示补偿，保留用户最小化
  和移动状态。没有目标窗口的完成确认时，800 毫秒保护预算后仍标为“未确认”，
  并保留小型恢复记录；未确认不等于窗口一定恢复失败。正常交接不走此保守分支。
以下 r7 修复继续保留：

  哈希及本地会话验证。增加固定阶段/错误码记录，不导出路径、进程号或异常正文。
- 报告分别显示最近完整启动耗时和后续重复点击失败，避免旧的播放成功记录掩盖新问题。
- 可选安装绑定当前用户原官方桌面快捷方式；日常普通权限启动，卸载可核验后还原。
- 上次报告的完整启动约 30.7 秒，约 18 秒在等待客户端页面和布局就绪。此包不通过
  删除动画、降低画质或缩短必要校验等待来掩盖慢启动，也不保证每台电脑启动更快。
以下 r6 修复继续保留：
